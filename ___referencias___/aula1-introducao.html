00 — de onde veio o termo

O que é vibe coding?

É programar guiando-se pela intenção, não pela sintaxe: você descreve o que quer, acompanha o resultado e ajusta — em vez de escrever cada linha manualmente.

🧑‍🔬 Quem cunhou o termo

Andrej Karpathy — pesquisador de IA, cofundador da OpenAI e ex-diretor de IA da Tesla — publicou em 2 de fevereiro de 2025 um post na rede X descrevendo esse jeito de programar. O post viralizou (mais de 4,5 milhões de visualizações) e, no fim daquele ano, "vibe coding" foi eleita palavra do ano pelo dicionário Collins.

🗨️ Karpathy resumiu sua ideia original como algo como: "fully give in to the vibes, embrace exponentials" — ou seja, aceitar as sugestões da IA e confiar no processo, sem revisar linha a linha.

💡 Ele descrevia esse estilo para projetos pessoais e protótipos descartáveis — não para sistemas de produção. Isso importa, e vamos voltar nesse ponto mais tarde na aula.

00 — o fluxo na prática

O LLM está no meio do processo

Você continua no controle nas duas pontas: quem descreve a intenção e quem valida o resultado é sempre humano.

🎯 O LLM é o motor do meio, não o piloto. Ele traduz intenção em código — mas quem decide se esse código presta é sempre você.
01 — contexto histórico

De cabos físicos ao vibe coding

Clique em cada era para expandir os detalhes.

🔌
Anos 1940
Cabos físicos — programar era fiação
Máquinas como o ENIAC eram "programadas" reconectando cabos e chaves manualmente. Não existia teclado, tela nem linguagem — só hardware puro.
→ Um novo cálculo podia levar dias de reconfiguração física
→ Não havia separação entre "programa" e "máquina"
→ Cada pessoa que operava a máquina era, na prática, a engenheira de hardware
▶ clique para expandir
🗂️
Anos 1950
Cartões perfurados — instruções em papel
Instruções eram codificadas como furos em cartões, lidos em lote pela máquina. Sem interatividade: você entregava a pilha de cartões e esperava o resultado.
→ Um erro de digitação = perfurar o cartão de novo
→ Processamento em lote (batch), sem tela interativa
→ Ainda assim, um salto: separa "o que calcular" de "como calcular"
▶ clique para expandir
⚙️
Final dos 1950–60
Linguagens de baixo nível — Assembly
Mnemônicos (MOV, ADD, JMP) substituem os furos e fios, mapeando quase 1:1 com as instruções do processador.
→ Mais legível que binário puro, ainda muito ligado ao hardware
→ Código não portável entre arquiteturas diferentes
→ Exige entender o processador em detalhe
▶ clique para expandir
📘
1957 – 1970s
Linguagens de alto nível — programar fica humano
Fortran (1957), COBOL (1959) e depois C (1972) trazem uma sintaxe mais próxima da linguagem humana e portável entre máquinas.
→ Nasce a ideia de programar "sem pensar no hardware"
→ Compiladores traduzem a linguagem de alto nível para a máquina
→ Base para praticamente todas as linguagens modernas
▶ clique para expandir
🧩
Anos 1990–2000
Frameworks e APIs — montar em vez de construir do zero
Bibliotecas reutilizáveis, frameworks web e APIs REST transformam programar em "montar peças prontas" em vez de escrever tudo manualmente.
→ Frameworks como Rails e Django aceleram o desenvolvimento web
→ APIs permitem que sistemas diferentes conversem entre si
→ Gerenciadores de pacote (npm, pip) viram parte do dia a dia
▶ clique para expandir
✨
2021
Copilots — autocomplete com IA entra em cena
O GitHub Copilot chega ao público, sugerindo linhas e blocos de código com base no contexto do editor. Você ainda aceita ou rejeita cada sugestão.
→ Primeira vez que um LLM vira parte do fluxo diário de código
→ O controle ainda é manual: sugestão por sugestão
→ Prepara o terreno para o que vem a seguir
▶ clique para expandir
🌊
Fev/2025 – hoje
Vibe coding — a intenção vira o novo código-fonte
Karpathy nomeia o estilo de descrever intenção em linguagem natural e deixar o LLM gerar (e às vezes até rodar) o código.
→ Collins Dictionary elege "vibe coding" palavra do ano de 2025
→ Nascem ferramentas inteiras desenhadas em torno desse fluxo
→ Você está exatamente nesse capítulo agora
▶ clique para expandir

03 — três formas de vibe coding

Nem todo vibe coding é igual

O que muda entre os modos é onde o LLM roda e quanto do ambiente ele enxerga.

🧪
Protótipos
Você descreve o app e a ferramenta gera (e hospeda) uma versão funcional rapidamente. Ótimo para validar uma ideia ou um MVP, sem se preocupar com infraestrutura.
ReplitLovableBolt.newv0 (Vercel)
⌨️
CLI
O agente roda no terminal e edita arquivos direto no seu repositório existente — encaixa no fluxo que você já tem, com git, scripts e CI.
Claude CodeCodex CLI
🖥️
IDEs com harness
Um editor completo com um agente que enxerga múltiplos arquivos, roda comandos e conversa com você por chat lateral — o ambiente inteiro vira o "harness" do agente.
CursorAntigravityWindsurfVS Code + extensões

Existem vários outros — o cenário muda rápido. O que importa é reconhecer a categoria, não decorar a lista.

04 — boas práticas (1/4)

A IA tem um papel — e não é o de chefe

🎯 IA não é autoridade, é assistenteA palavra final sobre o que vai pro código é sempre sua.
💡 IA sugere, você decideTrate cada resposta como um palpite qualificado, não uma ordem a seguir.
🤝 Confiança é diferente de delegarConfiar no resultado não significa parar de acompanhar o processo.
👤 Responsabilidade é humanaSe algo quebra em produção, quem responde por isso é você — não a IA.
04 — boas práticas (2/4)

Trabalhe em passos pequenos

🪜 Iterações passo a passoConstrua em pequenos ciclos — pedir, testar, ajustar — em vez de um salto gigante.
✏️ Prompts pequenosPeça uma coisa de cada vez, com clareza sobre o que você quer.
1️⃣ Uma mudança por vezFunciona muito melhor do que pedir tudo de uma vez — mais fácil de revisar e reverter.
🚧 Controle de escopoDefina antes o que a IA pode (e não pode) tocar naquele pedido.
04 — boas práticas (3/4)

Confiar não substitui validar

💾 Versionamento salvaCommits frequentes viram seu botão de desfazer quando algo dá errado.
🧪 Testar é obrigatórioCódigo gerado por IA também precisa de testes — talvez mais do que o seu.
▶️ Rode, teste e valideNunca aceite um trecho só porque "parece certo" na leitura.
⚡ Feedback rápidoQuanto antes você percebe um erro, mais barato é corrigi-lo.
04 — boas práticas (4/4)

A IA só sabe o que você conta

📎 Dê contexto e restriçõesExplique o cenário, as regras do projeto e o que não pode mudar.
🚫 Limites explícitosDiga claramente o que ela não deve tocar ou decidir sozinha.
📐 Exemplos a seguirMostrar um padrão já existente ajuda mais do que explicar em teoria.
📦 DependênciasInforme versões, bibliotecas e convenções do projeto antes de pedir código.
💭 Uma forma simples de lembrar tudo isso: imagine que você vai ter que explicar o projeto do zero, sempre, para uma pessoa nova que acabou de entrar no time. É basicamente assim que um LLM enxerga cada conversa nova.
05 — o modelo não sabe que não sabe

IA também alucina

O modelo otimiza para atender ao pedido, não para pensar em performance, impacto no sistema ou se aquilo realmente é necessário. Ele não sabe quando não sabe — e responde com a mesma confiança certo ou errado.

📦 Inventa APIs e bibliotecasPode citar métodos, parâmetros ou pacotes que não existem — com a mesma confiança de algo real.
🧩 Cria imports desnecessáriosImporta dependências que o projeto não usa, não tem instalada, ou nem precisa.
🍝 Gera código morto ou redundanteProduz funções, variáveis e trechos inteiros que nunca serão chamados.
🧪 Não testa sozinhoEntrega a solução como se estivesse pronta, mas não roda nem valida por conta própria.
⚠️ Sinais de alerta: código muito maior do que o esperado, imports que você nunca ouviu falar, funções que nunca são usadas em lugar nenhum, ou uma resposta confiante demais sobre algo que "parece" errado. Ler o diff inteiro — não só rodar e torcer — é o que separa vibe coding com cuidado de vibe coding no escuro.

07 — não aceite no escuro

Pergunte antes de aceitar

Entender o "porquê" é o que separa vibe coding responsável de simplesmente aceitar tudo cegamente.

Explique esse código.
Por que isso funciona?
Como você fez isso?
Quais são os trade-offs dessa escolha?
Que outras formas existem de fazer isso?
08 — dois contextos, dois rigores

Protótipo ≠ Produção

Vibe coding acelera os dois — mas o nível de cuidado exigido não é o mesmo.

RápidoO objetivo é validar uma ideia, não durar para sempre.
🎲

👁️

09 — o humano ainda coda

Saiba quando parar

Quando o agente entra em loop, insiste no caminho errado ou você já não entende mais o que está acontecendo — parar e recomeçar é uma opção válida, não uma derrota.

💭 Vibe coding não elimina a programação — muda onde você aplica sua atenção. Humanos ainda codam: escrevem trechos críticos à mão, reescrevem prompts, e decidem quando é hora de jogar fora e recomeçar.
